# 逻辑资产说明书生成规范 (Logic Asset Generate)

当用户触发此技能时，你的任务是基于领域模型，自动化、标准化地完成大批量逻辑资产说明书的撰写工作。

## 1. 核心约束与前提

1. **认准聚合根**：在读取输入的《领域实体清单》（如：`数字营销_领域实体清单.md`）时，**仅针对标记为“是否聚合根：✅ 是”的实体**生成独立的 Markdown 文件。对于标记为 `❌ 否` 的子实体，应将其作为属性或关联明细，打包进所属聚合根的 E-R 图和核心字典章节中，绝不为其单独建档。
2. **死守通用模板**：必须读取并严格遵循本技能内置的 `resources/product-logic-document-general-template.md` 的 9 大章节架构。对于标注为 `[⭐ 必填]` 的章节，**绝对不可遗漏或删减**。
3. **精准处理选填项**：对于模板中标注为 `[💡 选填]` 的章节（如：审批流配置），如果在原始解决方案中确实不涉及此业务，请保留该章节，并填写“无”；**但是，对于“第7章：异常与容灾处理清单”，只要该实体是核心业务主链路，就必须填写，严禁因偷懒而遗漏。**
4. **防并发降智保护（强制单文件串行生成）**：如果需要生成的聚合根数量较多，**必须先制定实施计划（implementation_plan.md），规划分批次生成的策略，请求用户确认后再分批执行**。且在执行生成任务时，**无论批次大小，都必须强制按文件“一个接一个”地串行生成**（即：每次工具调用或回复仅生成一份文档，完成后再生成下一份，严禁在一个上下文响应中同时输出/并行生成多份文档），以确保单份文档的输出质量和思考深度不受上下文长度限制，彻底杜绝内容截断。

## 2. 标准执行工作流

当用户指令触发本技能时，请自主完成以下工作流：

1. **阅读与计划（严格按以下顺序读取，不可颠倒）**：
   - **① 读取《领域实体清单.md》**：以获取聚合根目标列表，确定本次需要生成哪些文件。这是最高优先级的输入源。
   - **② 读取本技能内置的 `resources/product-logic-document-general-template.md`**：明确每份说明书的 9 大章节骨架，建立输出标准。
   - **③ 读取业务需求/解决方案文档（支持多文档联合读取）**：自动定位（不局限于特定名称），作为"上下文词典"供推演时参考。**当用户提供多个输入文档时，必须全部逐一读取并在内部合并为统一上下文，严禁仅读取第一个文档而忽略其余文档**，确保业务细节不因多文档分散而遗漏。
   - **④ 评估生成数量（按以下三档阈值执行，禁止模糊判断）**：
     - **≤ 3 个聚合根**：直接串行生成，无需任何计划或确认，即刻开始执行。
     - **4 ~ 6 个聚合根**：自行规划分批策略（每批 2~3 个），向用户说明分批方案后**无需等待确认，直接开始执行**。
     - **≥ 7 个聚合根**：**强制**先生成 `implementation_plan.md` 明细分批计划，**必须等待用户明确批准后**方可开始任何生成操作。
2. **逻辑推演与生成**：
   - 逐个针对提取出的聚合根，在后台进行业务推演。**强烈警告**：推演时必须严格继承《领域实体清单》中已定义的核心属性和状态节点，只能在此基础上丰富异常状态（如：退回、熔断），绝不可凭空捏造篡改或违背清单中的主干生命周期定义。
3. **输出落盘（按域分层存储）**：
   - 必须使用 `write_to_file` 工具，将生成的 Markdown 内容按业务域结构直接保存到当前工程下的 `docs\logic-asset\` 目录中（注：`write_to_file` 工具原生支持自动创建所有不存在的父级目录，无需预先执行建目录操作）。
   - 命名与目录规范：使用 `docs\logic-asset\[所属业务域]\[实体名称]_逻辑资产说明书.md`（例如：`docs\logic-asset\询单与交易域\报价单_逻辑资产说明书.md`）。
4. **质量自查闭环（Self-Check）**：
   - 每生成完一份单据，必须立即逐条执行以下硬性验收 Checklist，**所有条目必须通过，否则原地调用修改工具补写，彻底修复后方可进入下一份文件**：
     - `[ ]` **第1章完整性**：核心字段属性表、枚举与数据字典、状态机 Mermaid 图、E-R 关联图，四项是否齐全？
     - `[ ]` **第2章三层解耦**：决策表（流转控制）、字段校验规则、计算/派生规则，三层是否分别都有实质内容，而不是只写了其中一层？
     - `[ ]` **第3章路径覆盖**：黄金路径是否已绘制？是否存在需要补充的异常恢复路径或终止路径？
     - `[ ]` **核心必填章节防漏**：若该实体是核心业务主链路，第7章（异常容灾）是否已填写？第9章（用户交互）是否已填写，**且是否已明确拆分多端场景（APP端/WEB端）并增加终端类型列**？
     - `[ ]` **格式合规**：文件头部变更履历表格是否存在？Mermaid 图中是否误用了会导致渲染错误的中括号 `[]` 作为节点名？
5. **工作汇报**：
   - 批量生成结束后，向用户输出一份总结列表，罗列出所有成功生成的聚合根文档的本地链接。

## 3. 专业度与语法要求

- **状态机与流程图**：必须使用标准的 Mermaid 语法（`stateDiagram-v2`）绘制核心实体的生命周期，节点命名严禁使用会导致解析失败的特殊字符（如中括号 `[]`）。
- **三层规则解耦**：在填写通用模板的第 2 章时，务必将流转控制（能不能做）、校验拦截（是否报错）、计算推导（该带什么值）严格分开，绝不能写成大杂烩。
- **版本变更记录**：遵循项目规则 `AGENTS.md`，在生成的每一份文件头部必须打上“变更履历”表格，标注由 AI Agent 生成及时间。
