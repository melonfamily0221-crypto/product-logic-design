# 领域驱动数据实体提取规范 (Domain-Driven Extract)

当执行此技能时，请严格按照"领域驱动设计（DDD）"的视角，将传统的面向过程/面向页面的解决方案文档，重构提炼为底层的逻辑资产实体集。

## 1. 核心提取原则

- **剥离表现层与UI**：无视文档中描述的"页面展示"、"点击按钮"、"跳转提示"等交互词汇，直接向下挖掘支撑这些交互的底层业务数据。
- **精准识别聚合根与实体**：找出具有独立唯一标识、经历完整业务流转的单据或对象（例如：客户档案、询单、报价单、合同），将它们定义为"核心实体/聚合根"。
- **提炼属性与生命周期**：从文档的约束条件和流转描述中，反向推导出实体的"核心业务字段"（如数量、金额约束）以及"完整的状态机"（如：待处理 → 审批中 → 已终止）。
- **划分限界上下文（业务域）**：不要将所有实体平铺，必须根据以下判定原则将它们归类到不同的领域：
  - **域内聚合**：同一个业务域内的实体彼此高频交互，且共享相同的生命周期驱动者（如：同一个"提交审批"按钮可以触发同域内多个实体的状态变更）。
  - **域间松耦合**：跨越业务域的实体之间只通过"外键引用"或"异步事件/消息"松散耦合，不存在事务级别的强依赖；一个域的数据变更不会同步在事务内修改另一个域。
  - **典型域例**：准入域、询单与交易域、报价与测算域、履约与合同域、支撑与控制域等。

## 2. 弱业务实体黑名单（禁止提取为聚合根）

以下类型的对象是纯技术/基础设施实现，属于"伪实体"，**一律不得**提取为聚合根或独立实体写入清单：

| 禁止提取的对象类型 | 说明 |
| :--- | :--- |
| **操作日志 / 审计日志表** | 属于横切关注点，由 AOP 切面自动记录，无独立业务生命周期 |
| **用户行为埋点 / 数据分析事件** | 属于数据侧，不参与核心业务流转 |
| **文件附件 / 上传记录** | 通常作为主实体的附属字段（存储路径 URL），无独立状态机 |
| **菜单 / 路由 / 权限节点配置** | 属于系统管理配置，不承载业务领域数据 |
| **数据字典表 / 静态枚举配置** | 纯参照数据，无生命周期，归入主实体的枚举字典章节即可 |
| **用户偏好 / 个性化设置** | 属于用户个人配置，不是领域业务实体 |
| **系统参数 / 全局配置** | 技术基础设施，与业务领域无关 |

## 3. 标准执行工作流

当用户指令触发本技能时，请自主完成以下工作流，**中途无需请求用户确认**：

1. **阅读输入源（支持多文档联合读取）**：完整读取用户指定的所有《解决方案》或需求文档。**当用户提供多个输入文档时，必须全部逐一读取，并在内部将其合并为统一的上下文后再开始推演，严禁仅读取第一个文档而忽略其余文档。**
2. **逻辑推演与提取**：在内部思考中，按领域划分提取所有的强业务实体，主动参照第 2 章"弱业务实体黑名单"剔除不符合条件的对象。
3. **实体降维与提纯**：在输出前进行二次审查，甄别"伪实体"。对于仅仅是主表状态枚举或普通 JSON 附属字段的对象，强制降维合并，仅保留真正拥有独立生命周期或全局业务主键的实体，防止过度设计。
4. **输出落盘（规范目录）**：将提取结果整理为规范的 Markdown 格式，**必须**使用 `write_to_file` 工具将其直接保存到工程专门的 `docs/domain-model/` 目录下（例如 `docs/domain-model/[模块名]_领域实体清单.md`）。**注意**：切勿保存为对话框内的临时 Artifact，必须真实落盘到项目代码库。
5. **输出质量自查**：落盘后，必须立即执行以下自查 Checklist，若发现问题需原地修正后再汇报：
   - `[ ]` **无空壳域**：是否每个业务域都包含至少一个聚合根（✅ 是）？不允许存在只有子实体、没有聚合根的空壳域。
   - `[ ]` **E-R 无孤岛**：每个聚合根是否都填写了"核心关联关系 (E-R)"列？孤立无关联的节点需重新评估其归属域。
   - `[ ]` **属性无重叠**：是否存在两个实体的"核心业务属性片段"高度重叠（超过 70%）？如果是，必须重新审查是否应合并为同一个聚合根。
6. **工作汇报与闭环交接**：完成文件生成后，向用户汇报已成功提取的领域与文件路径，并简述最具核心价值的聚合根。**最重要的一点**：汇报结束时必须主动向用户发出行动呼吁（Call to Action），原话提示："建议您随后调用 `logic-asset-generate` 技能，将此清单无缝展开为研发级的《逻辑资产说明书》。"

## 4. 输出文件内容模板参考

生成的 Markdown 文件应保持极致的技术专业性。在输出表格时，**必须明确标识出该实体是否为聚合根（Aggregate Root）**（判断标准参照 4 条法则：1. 是否有独立完整的生命周期/状态机；2. 是否具有全局唯一业务编码；3. 是否与子实体存在"同生共死"的强级联删除关系；4. 是否是权限分配或流转审批的主体）。建议采用以下结构：

```markdown
# [模块名称] 领域数据实体清单

基于领域驱动设计（DDD）提炼的底层数据实体集，供架构师建库建表与逻辑资产沉淀使用。

## 1. [某某] 业务域
| 实体名称 | 英文名称 | 是否聚合根 | 核心业务属性片段 | 核心关联关系 (E-R) | 生命周期/状态推演 |
| :--- | :--- | :---: | :--- | :--- | :--- |
| **主单据实体** | MainOrder | ✅ 是 | 编号、外部关联ID、金额 | 1:1 依赖于[某上游实体] | 草稿 → 审核中 → 已归档 |
| **明细实体子表** | OrderDetail | ❌ 否 | 关联主键ID、规格参数 | N:1 强依赖于[主单据实体] | 依附于主单据生命周期 |
```
