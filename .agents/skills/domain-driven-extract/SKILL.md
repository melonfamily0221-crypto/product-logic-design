# 领域驱动数据实体提取规范 (Domain-Driven Extract)

当执行此技能时，请严格按照"领域驱动设计（DDD）"的视角，将传统的面向过程/面向页面的解决方案文档，重构提炼为底层的逻辑资产实体集。

## 1. 核心提取原则

- **剥离表现层与UI**：无视文档中描述的"页面展示"、"点击按钮"、"跳转提示"等交互词汇，直接向下挖掘支撑这些交互的底层业务数据。
- **精准识别聚合根与实体**：找出具有独立唯一标识、经历完整业务流转的单据或对象（例如：客户档案、询单、报价单、合同），将它们定义为"核心实体/聚合根"。
- **提炼属性与生命周期**：从文档的约束条件和流转描述中，反向推导出实体的"核心业务字段"（如数量、金额约束）以及"完整的状态机"（如：待处理 → 审批中 → [已终止]）。
  > **状态机终态标注规范**：终态节点（不可再流转的最终状态）须用 **方括号** 标注，例如：`待审核 → 审核通过 → [已同步]`、`审批中 → 审批驳回 / [已归档]`。这是后续 `logic-asset-generate` 技能正确生成状态机图的前提。
- **划分限界上下文（业务域）**：不要将所有实体平铺，必须根据以下判定原则将它们归类到不同的领域：
  - **域内聚合**：同一个业务域内的实体彼此高频交互，且共享相同的生命周期驱动者（如：同一个"提交审批"按钮可以触发同域内多个实体的状态变更）。
  - **域间松耦合**：跨越业务域的实体之间只通过"外键引用"或"异步事件/消息"松散耦合，不存在事务级别的强依赖；一个域的数据变更不会同步在事务内修改另一个域。
  - **典型域例**：准入域、询单与交易域、报价与测算域、履约与合同域、支撑与控制域等。

## 2. 弱业务实体黑名单（禁止提取为聚合根）

以下类型的对象是纯技术/基础设施实现，属于"伪实体"，**一律不得**提取为聚合根或独立实体写入清单：

| 禁止提取的对象类型 | 说明 |
| :--- | :--- |
| **操作日志 / 审计日志表** | 属于横切关注点，由 AOP 切面自动记录，无独立业务生命周期 |
| **用户行为埋点 / 数据分析事件** | 属于数据侧，不参与核心业务流转 |
| **文件附件 / 上传记录** | 通常作为主实体的附属字段（存储路径 URL），无独立状态机 |
| **菜单 / 路由 / 权限节点配置** | 属于系统管理配置，不承载业务领域数据 |
| **数据字典表 / 静态枚举配置** | 纯参照数据，无生命周期，归入主实体的枚举字典章节即可 |
| **用户偏好 / 个性化设置** | 属于用户个人配置，不是领域业务实体 |
| **系统参数 / 全局配置** | 技术基础设施，与业务领域无关 |
| **审批流实例 / 审批记录** | 属于流程引擎的运行时数据，由审批流管理引擎统一管理，不在领域层建立独立聚合根；仅在主业务实体（如报价单、成交方案）中记录"审批状态"字段即可 |

> **灰色地带判定原则**：若某对象的状态变更会**直接触发核心业务流转**（而非仅仅记录或配置），则应纳入领域模型。例如：影响价格策略的"客户等级"本身是枚举配置（黑名单），但"客户等级变更申请单"若有独立审批流程，则应纳入为聚合根。

## 3. 防遗漏交叉验证心法 (Anti-Omission Cross-Validation)

> ⚠️ **执行时机强制约束**：本章4项验证必须在工作流 **Step 2 逻辑推演完毕、Step 4 降维审查之前** 作为独立的 Step 3 强制执行。禁止跳过。

1. **状态机溯源法（最有效）**：全文扫描所有业务状态（如：待审批、已生效、已失效）。针对每个状态倒推："究竟是哪个底层数据载体在经历这个状态？"如果没有实体能明确承载该状态，则必然遗漏了聚合根（例如从"报价已失效"推导出独立的《对外正式报价单》）。
2. **名词与动词剥离法**：提取核心业务动词（如：议价、下发、评估），寻找承受该动作的名词客体。如果业务动作没有落库的数据支撑，说明存在实体遗漏。
3. **角色操作盲区比对**：遍历所有出现的业务角色（如业务员、技术员、审批人）。每个角色必定有其主导操作的"核心单据"。若某角色的工作成果在现有模型中无处存放，则需补充相应实体（如：为技术员补充《技术条款》子表）。
4. **事件风暴与上下游血缘校验**：检查流程节点间的数据流转与领域事件。如果上游的数据在进入下游节点时发生了结构突变或侧重点转移，说明中间缺少了过渡/快照实体（例如从内部测算到最终成交的裂变）。

## 4. 标准执行工作流

当用户指令触发本技能时，请自主完成以下工作流，**中途无需请求用户确认**：

1. **阅读输入源（支持多文档联合读取）**：完整读取用户指定的所有《解决方案》或需求文档。**当用户提供多个输入文档时，必须全部逐一读取，并在内部将其合并为统一的上下文后再开始推演，严禁仅读取第一个文档而忽略其余文档。**

2. **逻辑推演与提取**：在内部思考中，按领域划分提取所有的强业务实体，主动参照第 2 章"弱业务实体黑名单"剔除不符合条件的对象。

3. **[强制] 执行第3章4项交叉验证**：逐一对当前已提取的实体列表执行"状态机溯源法"、"名词动词剥离法"、"角色操作盲区比对"、"事件风暴血缘校验"四项检查。对每项验证均须在内部思维中给出明确的通过/补充结论，确认无遗漏后才可进入下一步。

4. **实体降维与子实体显性化**：在输出前进行二次审查，甄别"伪实体"。对于仅仅是主表状态枚举或普通单值字段的对象，强制降维合并。**但是，对于那些结构复杂、由不同角色在不同节点录入、或者需要独立细化逻辑的"子实体（Sub-entity）"或"值对象（Value Object）"（如：报价单下的成本核算明细、询单下的技术评估条款等），必须在清单中将它们明确列出，并在"实体类型"列中标注为 `🔵 子实体` 或 `🟡 值对象`**。保留它们有助于指导后续拆表或复杂的 JSON 结构设计，防止单表过度臃肿。

5. **输出落盘（规范目录）**：将提取结果整理为规范的 Markdown 格式，**必须**使用 `write_to_file` 工具将其直接保存到工程专门的 `docs/domain-model/` 目录下（例如 `docs/domain-model/[模块名]_领域实体清单.md`）。**注意**：
   - 切勿保存为对话框内的临时 Artifact，必须真实落盘到项目代码库。
   - **若目标文件已存在**，须遵循项目 `.agents/AGENTS.md` 中的版本迭代规范，**不得原地覆盖**，应创建新版本文件（如 `_v2`），并在文件头"变更履历"中记录修改日期、执行人（AI Agent）与核心变更点。

6. **输出质量自查**：落盘后，必须立即对以下4项逐条给出明确的检查结论（通过 / 问题描述），若发现问题需原地修正后再汇报：
   - **[检查1] 无空壳域**：每个业务域都包含至少一个聚合根（🟢 聚合根）？不允许存在只有子实体、没有聚合根的空壳域。
   - **[检查2] E-R 无孤岛**：每个聚合根是否都填写了"核心关联关系 (E-R)"列？孤立无关联的节点需重新评估其归属域。
   - **[检查3] 子实体提炼**：是否已将那些结构复杂、需要独立记录或权限管控的子实体/值对象提取出来，并正确标注实体类型且指明其依附的主单据？
   - **[检查4] 属性无重叠**：是否存在两个实体的"核心业务属性片段"高度重叠（超过 70%）？如果是，必须重新审查是否应合并为同一个聚合根。

7. **工作汇报与闭环交接**：完成文件生成后，向用户汇报已成功提取的领域与文件路径，并简述最具核心价值的聚合根。**最重要的一点**：汇报结束时必须主动向用户发出行动呼吁（Call to Action），原话提示："建议您随后调用 `logic-asset-generate` 技能，将此清单无缝展开为研发级的《逻辑资产说明书》。"

## 5. 输出文件内容模板参考

生成的 Markdown 文件应保持极致的技术专业性。在输出表格时，**必须明确标识出该实体的类型**（聚合根判断标准参照 4 条法则：1. 是否有独立完整的生命周期/状态机；2. 是否具有全局唯一业务编码；3. 是否与子实体存在"同生共死"的强级联删除关系；4. 是否是权限分配或流转审批的主体）。

**实体类型图例**：

| 标识 | 实体类型 | 含义 |
| :---: | :--- | :--- |
| 🟢 聚合根 | Aggregate Root | 有独立生命周期与全局唯一ID，是权限与审批的主体 |
| 🔵 子实体 | Sub-entity | 结构复杂、需独立建表，但依附于聚合根存在 |
| 🟡 值对象 | Value Object | 无独立ID，嵌入主实体存储（JSON或内嵌字段），描述聚合根的某一属性集 |
